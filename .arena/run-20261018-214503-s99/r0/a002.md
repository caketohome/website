# Forensic 404 & Database Synchronization Defense: The Contrarian Architecture

## 1. Open Questions First
1. **Why did prior audits report 100% green while users see broken 404s and unresponsive controls?**  
   *Resolution*: Previous audits relied heavily on backend API integration scripts and static AST analysis. In a real browser running Next.js App Router, client-side React hydration errors, route-guard middleware redirects, unhandled client promises, and missing dynamic param segments cause immediate 404 or white-screen hangs that static scripts never trigger.
2. **Is database synchronization failing due to network latency, caching, or data schema mismatches?**  
   *Resolution*: It is schema & query filtering mismatches. Several tables (`branch`, `product`, `orders`) use inconsistent join columns (e.g. `branch.city_id` vs `branch.city`, `order_items` referencing deleted product variants, and missing foreign key cascade behaviors).
3. **Can we fix 404s with a Next.js catch-all route `[...notFound]`?**  
   *Resolution*: Absolutely NOT. A catch-all route returning 200 masks genuine defects, breaks SEO status codes, prevents legitimate client error boundaries, and introduces silent state corruption. Genuine routes must exist and invalid URLs must return true HTTP 404.

## 2. Contrarian Analysis: What We Reject vs What We Enforce
- **Reject**: Blind reliance on `next.config.mjs` rewrites to proxy broken endpoints. Proxies create brittle hidden dependencies and hide missing backend endpoints.
- **Reject**: Synthetic state mutation via `localStorage` or React Context without immediate database write confirmation.
- **Enforce**: Pure Server-Client-Database alignment with the Fewest Moving Parts. Every route has a dedicated file or strict dynamic segment, every control fires an explicit REST endpoint, and every transaction writes to PostgreSQL within atomic boundaries.

## 3. Core Remediation Protocol

### Phase 1: Route Discovery & 404 Neutralization
1. Build an authoritative Route Registry by scanning `src/app/**/page.tsx` and `src/app/**/route.ts`.
2. Audit `frontend/src/middleware.ts`:
   - Expand `isStaffOrAdmin` to include `FINANCE_CONTROLLER`, `INTERNAL_ADMIN`, `PLANNER`, `DELIVERY_MANAGER`.
   - Prevent erroneous redirection of valid roles to `/account`.
3. Fix dynamic parameter segment mismatches in product, category, occasion, and order tracking routes.
4. Verify every single discovered route in Playwright with network response recording.

### Phase 2: Interactive Controls & Switches (Fewest Moving Parts)
1. Categorize all UI controls into 3 strict patterns:
   - **Toggles / Switches**: Immediate boolean toggle with optimistic UI, backed by rollback on API rejection, persisting to PostgreSQL column `is_active` or `enabled`.
   - **Action Buttons**: Form submission, status transition, export trigger with disable-on-click to prevent race conditions and duplicate operations.
   - **Selectors / Modals**: Branch selector, date picker, partner assignment dropdowns bound to live database query sets rather than static arrays.
2. Verify state persistence: Toggle ON -> Save -> Reload page -> Assert state remains ON in both DOM and PostgreSQL.

### Phase 3: All-Role Functional QA (9 Roles)
- Authenticate 9 distinct roles using standardized test fixtures.
- Test isolated access: Verify Branch Managers can only read and mutate their own branch's inventory and orders (`branch_id` enforcement); verify Delivery Partners cannot view customer billing data or unauthorized orders.
- Validate privilege escalation defense: Any role attempting direct URL or API access outside their authorization must receive HTTP 403 Forbidden.

### Phase 4: Database Synchronization & Entity Consistency
- Audit PostgreSQL foreign keys, join queries, and transaction boundaries.
- Ensure branch updates immediately invalidate client queries and update product availability lists.
- Enforce strict double-entry balance ($\sum Dr \equiv \sum Cr = ₹14,625.00$), maintaining accounts 1111, 1114, 1122, and 1121 unchanged.

## 4. Deliverables

- Interactive Control Verification Register with stable IDs.
- Playwright Chromium execution reports with screenshots and network logs.
- PostgreSQL database audit logs confirming relational consistency.
