# Forensic Database Recovery and Catalog Restoration Architecture (Plan a001)

## 1. Open Questions & Architectural Resolutions
1. **Q: How did test and audit records contaminate the primary catalog in `public.product`?**  
   *Resolution*: Previous E2E test suites and forensic scripts executed direct SQL inserts without test-database isolation or post-test rollback hooks. Because `public.product` lacks a dedicated `is_test_record` discriminator, any record where `deleted_at IS NULL` is immediately ingested by `ProductRepository` and exposed to storefront categories and search.
2. **Q: Can synthetic audit records be safely hard-deleted from `cth_test`?**  
   *Resolution*: Only if they possess zero incoming foreign keys in `order_item`, `order_line_item`, `invoice_allocation_log`, and `branch_inventory`. If a synthetic test product was purchased in a previous test order, it must NOT be hard-deleted (which would violate relational integrity or destroy historical order traces); instead, it must be deactivated and soft-deleted (`deleted_at = NOW()`, `is_active = false`).
3. **Q: Why does the Admin Dashboard display placeholder GSTIN `29AAAAA0000A1Z5`?**  
   *Resolution*: The admin reporting API fallback or mock route was left wired to a static sandbox GSTIN rather than resolving from `public.gst_registration` or `public.company`.
4. **Q: Which of the 20 empty tables are safe candidates for cleanup?**  
   *Resolution*: Only scaffolded tables with 0 incoming foreign keys, 0 active domain services, and zero migration locks can be dropped. Double-entry accounting tables (`accounting_journal_entry`, `accounting_journal_line`, `accounting_fiscal_period`) must be retained even with 0 rows to preserve the integrity of the accounting subsystem.

## 2. Forensic Reconstruction: Invoicing & Accounting Changes
Between commits `ed74820` and `d231cee`, the database schema expanded to support financial double-entry bookkeeping, corporate gifting, and tax-compliant invoice sequences:
- Added `accounting_account` (98 rows), `accounting_voucher` (2 rows), and supporting journal structures.
- Added statutory invoice structures: `invoice` (71 rows), `invoice_sequence` (7 rows), and `invoice_allocation_log` (221 rows).

## 4. Table Cleanup Register
Of the 40 tables, 20 contain live records and are strictly retained. The 20 empty tables are classified defensively:
- **RETAINED (Financial & Core Domain Architecture)**:
  - `accounting_fiscal_period`, `accounting_journal_entry`, `accounting_journal_line`: Double-entry accounting ledger.
  - `inventory_movement`, `inventory_cost_consumption`, `inventory_cost_lot`, `purchase`, `purchase_item`, `supplier`: ERP inventory lot tracking.
  - `customer_address`, `customer_favorite`, `delivery_zone`, `offer`, `product_review`: Storefront customer domain.
- **SAFE DROP CANDIDATES (Proven Redundant/Obsolete Scaffolds)**:
  - `order_sequence`: Redundant with timestamp/CUID order numbering; zero FKs.
  - `popup_campaigns`, `popup_versions`: Scaffolds superseded by API-driven popups; zero FKs.
  - `cms_homepage_section`, `cms_page`: Scaffolded tables superseded by file-backed CMS engine; zero FKs.
  - `setting`: Empty legacy key-value store; zero FKs.
All drops are executed using `DROP TABLE IF EXISTS "table_name" RESTRICT;` inside a dedicated transaction.
