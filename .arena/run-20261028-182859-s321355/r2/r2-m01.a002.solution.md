# Forensic Database Restoration, Schema Cleanup & Integrity Recovery Architecture (Champion Solution a002)

## 1. First-Principles Diagnostic & Root Cause Reconstruction
A production e-commerce application requires strict referential and transactional isolation:
1. **Genesis of Regression**: During commits `ed74820` through `d231cee`, double-entry accounting ledgers (`accounting_account`, `accounting_voucher`) and statutory invoicing structures (`invoice`, `invoice_sequence`, `invoice_allocation_log`) were integrated.
2. **Catalog Contamination**: Integration and persistence tests inserted synthetic test records directly into `public.product` (e.g. `audit_prod_1787988674049`, `DB PERSISTENCE TEST 1788349863724`, `Sanity Test Cake (Edited) 1788353846663`, `RED VELVET DREAM CAKE [FORENSIC_DB_AUDIT_...]`). Because `frontend/src/lib/repositories/product.repository.ts` selects products where `deleted_at IS NULL AND is_active = true`, these test cakes polluted public collections, search results, and category counts.
3. **Admin Analytics Placeholder**: The admin analytics panel rendered placeholder GSTIN `29AAAAA0000A1Z5` due to a mock fallback in `frontend/src/lib/services/gst-reporting.service.ts` rather than resolving active registrations from `public.gst_registration`.
4. **Scaffolded Database Schema**: 40 tables exist in `public`. 20 have live records. Of the 20 empty tables, 14 represent legitimate domain structures (double-entry ledger and inventory cost lots), while 6 are obsolete, unreferenced prototypes (`order_sequence`, `popup_campaigns`, `popup_versions`, `cms_homepage_section`, `cms_page`, `setting`).

## 2. Options Matrix for Database Remediation

| Option | Strategy | Safety Rating | Blast Radius | Decision |
|---|---|---|---|---|
| **A. Complete DB Reset / Reseed** | Truncate schema and run migrations | CRITICAL RISK | Destroys 123 orders, 71 invoices, 36 payments, 98 accounts | **REJECTED** |
| **B. Blanket Hard DELETE** | `DELETE FROM product WHERE title LIKE '%TEST%'` | HIGH RISK | Violates foreign keys if test orders reference products | **REJECTED** |
| **C. Dual-Stage Soft-Delete & Safe Unreferenced Purge** | Mark all synthetic cakes `deleted_at = NOW(), is_active = false`; delete only proven unreferenced rows | MAXIMUM SAFETY | Zero disruption to historical orders/invoices; 100% clean storefront | **APPROVED** |
| **D. Blind Table Drop on all 0-row tables** | Drop all 20 empty tables | HIGH RISK | Drops enterprise double-entry accounting ledger schemas | **REJECTED** |
| **E. Evidence-Based Table Drop on Obsolete Scaffolds** | Drop only 6 unreferenced, empty prototype tables with `RESTRICT` | MAXIMUM SAFETY | Removes obsolete clutter while preserving enterprise modules | **APPROVED** |

## 3. Concrete Implementation Steps

### 3.1 Verified Pre-Flight Backup Gate
Database target: Isolated PostgreSQL 16 on `127.0.0.1:5433/cth_test` (role `cth_test_user`).
Verified dual-format backup verified prior to mutations:
- JSON snapshot: `backups/cth_test_backup_20261028_phase3_0.json` (1.12 MB, 1,296 records across 40 tables)
- SQL DDL & INSERT dump: `backups/cth_test_backup_20261028_phase3_0.sql` (0.81 MB)

### 3.2 Transactional Safe Table Drop
Execute in a single transaction using `RESTRICT` (never `CASCADE`):
```sql
BEGIN;
DROP TABLE IF EXISTS public.order_sequence RESTRICT;
DROP TABLE IF EXISTS public.popup_versions RESTRICT;
DROP TABLE IF EXISTS public.popup_campaigns RESTRICT;
DROP TABLE IF EXISTS public.cms_homepage_section RESTRICT;
DROP TABLE IF EXISTS public.cms_page RESTRICT;
DROP TABLE IF EXISTS public.setting RESTRICT;
COMMIT;
```
All remaining 14 empty tables (including accounting journals and inventory lots) are strictly retained.

### 3.3 Dual-Stage Synthetic Product Catalog Remediation
Step 1: Defensively soft-delete all synthetic test products so they are immediately excluded from all public queries:
```sql
UPDATE product 
SET is_active = false, deleted_at = NOW() 
WHERE id LIKE 'audit_prod_%' 
   OR id LIKE 'prod_1788%' 
   OR id LIKE 'prod_dist_test_%'
   OR title ILIKE '%TEST%' 
   OR title ILIKE '%AUDIT%';
```
Step 2: Cleanly purge unreferenced variants, options, and inventory without foreign key hazards:
```sql
BEGIN;
DELETE FROM branch_inventory WHERE product_id IN (
    SELECT id FROM product 
    WHERE deleted_at IS NOT NULL 
      AND id NOT IN (SELECT product_id FROM order_item WHERE product_id IS NOT NULL)
      AND id NOT IN (SELECT product_id FROM order_line_item WHERE product_id IS NOT NULL)
);
DELETE FROM variant_option WHERE variant_id IN (
    SELECT id FROM product_variant 
    WHERE product_id IN (
        SELECT id FROM product 
        WHERE deleted_at IS NOT NULL 
          AND id NOT IN (SELECT product_id FROM order_item WHERE product_id IS NOT NULL)
          AND id NOT IN (SELECT product_id FROM order_line_item WHERE product_id IS NOT NULL)
    )
);
DELETE FROM product_variant WHERE product_id IN (
    SELECT id FROM product 
    WHERE deleted_at IS NOT NULL 
      AND id NOT IN (SELECT product_id FROM order_item WHERE product_id IS NOT NULL)
      AND id NOT IN (SELECT product_id FROM order_line_item WHERE product_id IS NOT NULL)
);
DELETE FROM product WHERE deleted_at IS NOT NULL 
  AND id NOT IN (SELECT product_id FROM order_item WHERE product_id IS NOT NULL)
  AND id NOT IN (SELECT product_id FROM order_line_item WHERE product_id IS NOT NULL);
COMMIT;
```
