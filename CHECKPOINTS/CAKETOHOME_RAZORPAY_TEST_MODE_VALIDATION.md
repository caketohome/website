## 2. Zero-Credential Secret Management Audit

A forensic scan of the codebase, Git tree, and API responses verified zero plaintext credential leakage:

1. **Git Repository Cleanliness:** No Razorpay secrets, test keys, or private tokens exist in any committed files. `.env.local` and `.db_conn` are strictly gitignored in `.gitignore`.
2. **Server-Side Encryption Envelope:**
   - Secrets persisted in `public.payment_gateway_config` use versioned AES-256-GCM envelope encryption (`v1$iv$authTag$ciphertext`).
   - The master encryption key is derived server-side via `process.env.PAYMENT_CONFIG_MASTER_KEY`.
   - Plaintext keys never touch disk or database logs.
3. **API Redaction Guarantees:**
   - `GET /api/v1/admin/payments/razorpay/config` returns only masked identifiers:
     ```json
     {
       "success": true,
       "config": {
         "provider": "razorpay",
         "environment": "TEST",
         "key_id": "rzp_test_TxymYPGydaHJBL",
         "is_active": true,
         "has_key_secret": true,
         "has_webhook_secret": true,
         "last_tested_at": "2026-11-11T09:30:43.734Z"
       }
     }
     ```
   - No `key_secret` or `webhook_secret` is ever returned in client payloads or error traces.
4. **Client-Side Bundle Isolation:**
   - Only `NEXT_PUBLIC_RAZORPAY_KEY_ID="rzp_test_TxymYPGydaHJBL"` is exposed to the browser for mounting Razorpay Standard Checkout modal.

## 4. Payment Lifecycle & State Machine Transitions

The payment state machine was tested from creation through verification, idempotency, and refund handling:

```
┌─────────────┐     POST /order      ┌─────────────┐     Customer Auth     ┌──────────────┐
│   CREATED   │ ───────────────────> │  INITIATED  │ ────────────────────> │  AUTHORIZED  │
└─────────────┘                      └─────────────┘                       └──────────────┘
                                                                                  │
                                                                                  │ Signature / Webhook
                                                                                  ▼
┌─────────────┐     POST /refund     ┌─────────────┐     Atomic GL Post    ┌──────────────┐
│  REFUNDED   │ <─────────────────── │    PAID     │ <──────────────────── │   CAPTURED   │
└─────────────┘                      └─────────────┘                       └──────────────┘
```

### Verified State Transition Matrix
| From State | Trigger Event | To State | Database Effect | Empirical Status |
|---|---|---|---|---|
| `pending` | `POST /payments/razorpay/order` | `initiated` | Creates `payment_transaction` row with `gateway_order_id` | **VERIFIED** |
| `initiated` | Valid HMAC Signature | `paid` / `confirmed` | Updates `order.payment_status = 'paid'`, `status = 'confirmed'` | **VERIFIED** |
| `paid` | Duplicate Callback / Webhook | `paid` (No-op) | Intercepted idempotently; returns `{ idempotent: true }` | **VERIFIED** |
| `paid` | `POST /admin/payments/razorpay/refund` | `refunded` | Updates `payment_status = 'refunded'`, generates Credit Note | **VERIFIED** |

### Signature Verification Security
- Validates signature via constant-time comparison `crypto.timingSafeEqual` preventing timing attacks:
  $$\text{Expected} = \text{HMAC-SHA256}(\text{key\_secret}, \text{razorpay\_order\_id} \parallel "|" \parallel \text{razorpay\_payment\_id})$$
- Tampered signature probes were rejected with `HTTP 400 INVALID_PAYMENT_SIGNATURE`.

## 5. Webhook Idempotency & Out-of-Order Safety

1. **Duplicate Webhook Delivery:**
   - 5 identical webhooks dispatched simultaneously with identical event IDs.
   - Idempotency engine checked `public.outbox_consumer_receipt` and intercepted repeated events.
   - Result: Exactly 1 transaction processed, 4 returned `ignored_duplicate`.
2. **Out-of-Order Safety:**
   - Simulated a delayed webhook arriving *after* client-side signature verification already marked the order `paid`.
   - The state machine rejected state regression (does not transition `paid` back to `initiated` or re-deduct inventory).
